# Технологическая дорожная карта

Технологии и подходы из целевой архитектуры (Task 3) распределены по четырём зонам по аналогии с
технологическим радаром: **Adopt** (внедрять сейчас как стандарт), **Trial** (пилотировать на ограниченном
контуре), **Assess** (изучать, не внедрять до появления зрелости/потребности), **Hold** (сознательно не
использовать на данном горизонте).

## Adopt

| Технология / подход | Почему |
|---|---|
| MDM (Customer Hub + Reference Data) | Прямо закрывает главную проблему кейса — дубли клиентов и рассинхронизацию справочников; без него невозможна ни одна другая цель миграции |
| Airflow | Зрелый, широко распространённый оркестратор batch-пайплайнов, нужен уже в промежуточном состоянии (3 мес.) для простого DWH-пайплайна |
| DWH на PostgreSQL (промежуточное состояние) | Быстрый, знакомый инструмент, закрывает промежуточную регламентированную отчётность без риска для срока в 3 месяца |
| DataHub (каталог данных) | Требование трассируемости происхождения данных — сквозное ограничение проекта; чем раньше внедрён каталог, тем меньше "слепых зон" в дальнейшей миграции |
| Integration Layer (API Gateway/ESB) | Базовая инфраструктура для синхронного обмена, нужна уже на этапе 4 плана миграции, заменяет point-to-point интеграции RetailBank |

## Trial

| Технология / подход | Почему |
|---|---|
| Kafka + CDC (Debezium) | Новый для ландшафта RetailBank подход (там были только point-to-point интеграции); пилотируется на одном потоке (например, Транзакция → Lakehouse) перед распространением на все домены |
| Data Lakehouse (Apache Iceberg + Trino) | Технологически более сложный, чем DWH; пилотируется на конкретном сценарии — история карточных операций — прежде чем становиться основной платформой к 12 месяцам |
| Графовая БД для антифрода | Обосновано сущностью Контрагент, но графовые запросы — новая компетенция для команды; целесообразен пилот на ограниченном наборе антифрод-сценариев до полного разворачивания |
| Доменные data-продукты (элементы Data Mesh) | Организационная модель новая для банка; пилотируется на 1-2 доменах (например, Customer 360) до распространения на все пять продуктов из Task 3 |

## Assess

| Технология / подход | Почему |
|---|---|
| Полноценный Data Mesh (децентрализованная инфраструктура по доменам) | Требует зрелости платформы и организации, которой ещё нет сразу после слияния (см. `architecture-options.md` Task 3); стоит переоценить после стабилизации гибридной архитектуры, ориентировочно за пределами 12-месячного горизонта |
| MPP/колоночная СУБД как эволюция DWH (взамен PostgreSQL) | Если объём регламентированной отчётности вырастет за пределы возможностей PostgreSQL — этот вариант нужно будет оценить, но на 12-месячном горизонте достаточных данных для этого решения ещё нет |
| ML-платформа для риск-скоринга поверх Lakehouse | Ценность очевидна (данные уже консолидируются в Lakehouse), но не входит в цели этого проекта миграции данных; требует отдельной оценки после того, как Lakehouse станет стабильным источником |

## Hold

| Технология / подход | Почему |
|---|---|
| Point-to-point интеграции (подход RetailBank) | Прямо признаны источником проблем в кейсе — не развиваются и полностью выводятся из эксплуатации в рамках плана миграции |
| Сохранение двух параллельных DWH/BI (FU и RB) как постоянного решения | Допустимо только как временное состояние в переходный период; не может быть целевым решением — прямо противоречит цели "единая управленческая и регуляторная отчётность" |
| Ручное ведение справочников продуктов/тарифов/отделений в каждой CRM отдельно | Тот же подход, что привёл к текущей рассинхронизации; заменяется MDM Reference Data без промежуточных полумер |
| Хранение полной истории транзакций в реляционном DWH | Экономически и технически нецелесообразно при объёме двух банков — сознательно не рассматривается, история уходит в Lakehouse (см. `dwh-lakehouse.md` Task 3) |

## Как зоны связаны с горизонтами миграции

- Технологии **Adopt** разворачиваются в первую очередь (этапы 1-3 плана миграции) — это фундамент, на
  который опирается всё остальное.
- Технологии **Trial** появляются на этапах 4-6 — пилотируются на одном домене/потоке, чтобы снизить риск
  перед полным разворачиванием на всю организацию.
- Технологии **Assess** сознательно не входят в объём этого 12-месячного плана — они зафиксированы в
  дорожной карте как кандидаты для следующего цикла планирования, чтобы не размывать фокус текущей
  миграции.
- Подходы **Hold** — это явные "антипаттерны" из As-Is кейса, зафиксированные, чтобы команда не
  воспроизводила их случайно при консолидации (например, не заводила новый параллельный справочник вместо
  использования MDM).
