# Task 4. План миграции, cutover и технологическая дорожная карта — FinUnion + RetailBank

## Цель

Разработать план перехода от ландшафта As-Is к целевой архитектуре из Task 3: определить этапы миграции,
cutover-план для критичного домена, риски и митигации, а также технологическую дорожную карту.

## Структура

```

├── README.md                    — этот файл, резюме и навигация
├── migration-target-state.md    — образ целевого результата: что остаётся, выводится, мигрирует, переключается
├── migration-plan.md            — инкрементальный план миграции из 8 этапов
├── cutover-plan.md              — детальный cutover-план для домена "Клиентские данные"
```

## Краткое резюме решений

- **Целевой образ.** Остаются консолидированные Target Core/Card/Lending платформы, MDM, Integration
  Layer, Kafka, DWH, Data Lakehouse, BI, Airflow, DataHub. Выводятся RB CRM, RB Core, RB Cards, RB Loans,
  RB DWH, RB BI и все point-to-point интеграции RetailBank. Критерий завершения — 100% клиентов с единым
  golden client_id, отсутствие point-to-point потоков, DataHub со 100%-м покрытием lineage и минимум два
  успешных цикла параллельного прогона без критических расхождений.
- **План миграции** — 8 этапов от data discovery до вывода RB-систем и публикации доменных data-продуктов,
  с частичным распараллеливанием (например, простой DWH-пайплайн промежуточного состояния стартует, пока
  ещё продолжается клиентский матчинг).
- **Cutover-план** детально расписан для домена "Клиентские данные" (RB CRM/FU CRM → MDM Customer Hub) —
  от подготовки и data freeze до переключения, фолбэка и пост-cutover мониторинга; выбран как самый
  критичный домен, поскольку от golden client_id зависят все остальные.
- **Риски.** 7 рисков — от дублей клиентов и расхождения статусных моделей до нагрузки на OLTP от
  временных ETL/CDC-потоков и сопротивления команд RetailBank декомиссии систем, каждый — с митигацией.
- **Дорожная карта.** Технологии распределены по 4 зонам: Adopt (MDM, Airflow, DWH на PostgreSQL,
  DataHub, Integration Layer), Trial (Kafka/CDC, Data Lakehouse, графовая БД, доменные data-продукты),
  Assess (полноценный Data Mesh, MPP-эволюция DWH, ML-платформа), Hold (point-to-point интеграции,
  постоянное сосуществование двух DWH/BI, ручное ведение справочников, хранение полной истории транзакций
  в реляционном DWH).

## Как читать документы

Рекомендуемый порядок: `migration-target-state.md` → `migration-plan.md` (+ Gantt-диаграмма) →
`cutover-plan.md` (+ sequence-диаграмма) → `migration-risks.md` → `tech-roadmap.md`. Сначала фиксируется
"куда идём", затем — укрупнённые этапы, затем — детальный сценарий переключения одного критичного домена
как образец для остальных, далее — риски этого пути и, наконец, порядок внедрения технологий во времени.
