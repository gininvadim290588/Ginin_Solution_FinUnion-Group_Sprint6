# Task 2. Мастер-системы и потоки данных — FinUnion + RetailBank

## Цель

Определить мастер-системы для ключевых сущностей (из Task 1) на промежуточном и целевом горизонтах,
описать владение данными, построить диаграмму потоков данных (DFD) и описать управление этими потоками.

## Структура

```
Task2/
├── README.md                  — этот файл, резюме и навигация
├── master-systems.md          — мастер-системы по сущностям (3 мес. / 12 мес.) со ссылкой на BIAN
├── data-ownership.md          — Data Owner / Data Steward / Producer / Consumer по каждой сущности
├── data-flows.md              — описание основных потоков данных: источник, приёмник, действие, режим обмена
├── data-flow-management.md    — операционное управление потоками: SLA, владелец, качество, безопасность, мониторинг
├── data-dependencies.md       — 8 проблемных зависимостей и рисков на уровне данных
└── diagrams/
    └── data-flow-diagram.puml — DFD в формате PlantUML (промежуточное состояние, 3 мес.)
```

## Краткое резюме решений

- **Мастер-системы.** MDM назначен мастером только для клиентских и справочных данных — Клиент (MDM
  Customer Hub) и Продукт/Тариф/Отделение/Контрагент (MDM Reference Data). Счета, карты, кредиты, договоры,
  транзакции и платежи остаются в профильных банковских OLTP-системах (Core, Cards, Loans, Payment) — на
  3 месяца FU и RB системы остаются мастерами каждая для своего портфеля, на 12 месяцев происходит
  консолидация в единые целевые платформы. Обоснование для каждой сущности опирается на её BIAN-домен
  (Party Data Management → MDM, Current Account/Consumer Loan/Payment Execution → операционные системы).
- **Владение данными.** Для каждой из 12 сущностей определены Owner (бизнес-подразделение — Розница, МСБ,
  Риск-менеджмент, Финансовый департамент, Контактный центр, Юридический блок), Steward (преимущественно
  Data Office), Producer/Consumer и обязательные правила изменения и качества.
- **Потоки данных.** Описано 17 потоков, покрывающих все действия DFD (Create, Read, Update, Delete,
  Enrich, Validate, Aggregate): от клиентского матчинга в MDM и распространения golden record, через
  консолидацию в DWH/Lakehouse и антифрод-граф, до архивирования в объектное хранилище и регламентированной
  выгрузки регулятору как внешнему потребителю.
- **Управление потоками.** Для каждого потока определены SLA, владелец, контроль качества, требования к
  безопасности (шифрование, RBAC, маскирование, PCI DSS/AML-специфика) и способ мониторинга (дашборды
  задержки CDC, job-мониторинг ETL, алерты по контрольным суммам и SLA).
- **Риски.** Зафиксировано 8 проблемных зависимостей — от разных идентификаторов клиента и eventual
  consistency при публикации golden record до отсутствия Data Lake у RetailBank и нагрузки на OLTP от
  временных batch-потоков в переходный период.

## Как читать документы

Рекомендуемый порядок: `master-systems.md` → `data-ownership.md` → `data-flows.md` (+ диаграмма) →
`data-flow-management.md` → `data-dependencies.md`. Мастер-системы и владение задают "кто и где" отвечает
за данные, потоки и управление ими показывают "как данные физически перемещаются", а зависимости — "что
может пойти не так" при переходе от As-Is к целевому состоянию.
