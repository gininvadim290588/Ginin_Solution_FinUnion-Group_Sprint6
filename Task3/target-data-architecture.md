# Целевая архитектура данных (To-Be, 12 месяцев)

Диаграмма: `diagrams/target-architecture.puml`.

## Компоненты и их роль

### Operational Systems
Консолидированные операционные системы после миграции RetailBank: единая Core Banking платформа (счета,
договоры, транзакции), единая карточная платформа, единая Lending-платформа, Payment Hub, платформа
обработки обращений (Case). Это системы записи (systems of record) для операционных сущностей — Счёт,
Карта, Кредит, Договор, Транзакция, Платёж, Обращение — в соответствии с решением из Task 2 (MDM не
является для них мастером).

### MDM (Customer Hub + Reference Data)
Единственный источник золотых записей для Клиента, Продукта, Тарифа, Отделения и Контрагента. К 12 месяцам
MDM — не надстройка, а полноценная система записи для этих сущностей: операционные системы читают из него,
а не хранят собственные копии справочников.

### Integration Layer
Два режима обмена:
- **Синхронный** (API Gateway / ESB) — для операций, требующих немедленного ответа: проверка клиента при
  открытии продукта, запрос баланса, обращение к MDM за golden client_id в момент обслуживания клиента.
- **Асинхронный / CDC** (Debezium-коннекторы к операционным БД) — для распространения изменений без
  нагрузки на операционные системы, публикующих изменения в Kafka.

### Kafka (событийная шина)
Центральная шина для всех событийных потоков: изменения записей (CDC-топики), бизнес-события (новая
транзакция, платёж, обращение). Потребители — Data Lakehouse (потоковая запись), Graph DB (антифрод в
реальном времени), поисковый движок (индексация обращений).

### DWH
Регламентированная отчётность: управленческая и регуляторная. Содержит историзированные (SCD2) агрегаты и
факт-таблицы для BI и выгрузок регулятору. Наполняется через Airflow-пайплайны (batch/dbt) из операционных
систем и из Lakehouse (агрегация сырых событий).

### Data Lakehouse (Iceberg + Trino)
Большие исторические и событийные данные: полный поток транзакций, история карточных операций, клиентские
события каналов, сырьё для риск-моделей. Подробности — в `dwh-lakehouse.md`.

### BI
Дашборды и аналитика для бизнеса: обращается к DWH за регламентированными витринами и к Lakehouse (через
Trino) — за ad-hoc аналитикой на сырых/исторических данных.

### Airflow
Оркестрация всех batch-пайплайнов: загрузка в DWH, агрегация Lakehouse → DWH, архивация в объектное
хранилище, публикация lineage в DataHub.

### DataHub (каталог данных)
Каталог, lineage, владельцы данных. Получает метаданные от MDM, DWH, Lakehouse и Airflow — обеспечивает
требование "трассируемость происхождения данных" из ограничений проекта и делает видимой матрицу владения
из Task 2 (`data-ownership.md`).

## Принципы, заложенные в архитектуру

- **Разделение OLTP/OLAP.** Операционные системы никогда не читаются напрямую BI или регулятором — всегда
  через DWH/Lakehouse, что напрямую выполняет ограничение "аналитика не должна создавать нагрузку на
  операционные системы".
- **MDM как единственный источник golden record** для клиентских и справочных данных — устраняет проблему
  дублей и рассинхронизации, зафиксированную в кейсе.
- **CDC как основной механизм синхронизации** к 12 месяцам вместо batch-выгрузок 3-месячного
  промежуточного состояния — снижает задержку между операционными системами и аналитикой.
- **Единая точка каталогизации (DataHub)** для всех хранилищ обеспечивает трассируемость и совместима с
  доменной моделью владения (Task 2) и BIAN-доменами (Task 1).
- **Регулятор и клиентские каналы — внешние акторы**, не имеющие прямого доступа к внутренним хранилищам:
  регулятор получает только регламентированные выгрузки из DWH, каналы (мобильное/веб) взаимодействуют
  только с Operational Systems.
