# Аналитическая модель — область "Транзакции"

Выбрана область **Транзакции**, поскольку это самый объёмный и часто запрашиваемый аналитический домен
(BI-отчётность, риск-менеджмент, антифрод, регуляторная отчётность) и он напрямую связан с сущностью
Транзакция из Task 1 и потоками из Task 2. Диаграмма: `diagrams/star-schema-transactions.puml`.

## Выбор схемы: звезда

Выбрана **схема "звезда"** (не "снежинка"): измерения денормализованы — например, `dim_product` включает
атрибуты действующего тарифа напрямую, а не выносит их в отдельную нормализованную таблицу `dim_tariff`.

## Таблицы

| Тип таблицы | Пример | Гранулярность / назначение |
|---|---|---|
| Fact | `fact_transactions` | Одна строка на одну транзакцию |
| Dimension | `dim_customer` | Клиент, из MDM (SCD2 — история сегмента/KYC-статуса) |
| Dimension | `dim_account` | Счёт, по которому проведена операция |
| Dimension | `dim_card` | Карта (nullable — не у всех транзакций есть карта) |
| Dimension | `dim_product` | Продукт с денормализованными атрибутами тарифа (SCD2) |
| Dimension | `dim_branch` | Отделение, где инициирована операция (nullable для дистанционных каналов) |
| Dimension | `dim_channel` | Канал: офис / мобильное приложение / веб / контакт-центр |
| Dimension | `dim_counterparty` | Контрагент операции, включая признак совпадения с санкционным списком |
| Dimension | `dim_date` | Календарное измерение (год, квартал, месяц, признак рабочего дня) |

Ключевые атрибуты `fact_transactions`: `transaction_sk` (суррогатный ключ), `transaction_id` (натуральный
ключ из источника), внешние ключи на все измерения, `amount`, `currency`, `transaction_type`,
`is_fraud_flag`, `source_org` (признак FinUnion/RetailBank — важно на переходный период, пока портфели не
объединены физически).

## Почему звезда подходит для этой OLAP-нагрузки

- **Простота запросов для BI.** Основные потребители — BI-дашборды и регуляторная отчётность, где типичный
  запрос — агрегация `fact_transactions` по одному-двум измерениям (например, сумма операций по продукту и
  месяцу). Звезда требует минимум join'ов (факт + нужные измерения напрямую), что даёт предсказуемую
  производительность и простые SQL-запросы для аналитиков, не обязательно знакомых с нормализованными
  схемами.
- **Совместимость с BI-инструментами.** Большинство BI-инструментов (в т.ч. self-service) из коробки лучше
  работают со звездой: автоматически строят join'ы факт↔измерение без необходимости настраивать
  многоуровневые связи, как в снежинке.
- **Меньше объектов для governance.** Денормализованные измерения проще описать и закаталогизировать в
  DataHub как единый бизнес-объект ("Продукт с текущими условиями"), чем поддерживать нормализованную
  иерархию `dim_product → dim_tariff → dim_tariff_history`.
- **Снежинка была бы оправдана**, если бы Тариф часто анализировался отдельно от Продукта большим числом
  независимых запросов (например, отдельная тарифная аналитика) — в этом кейсе такой потребности не
  выявлено, поэтому денормализация в звезду выгоднее по производительности чтения, которая приоритетнее
  экономии места на измерениях.
- **SCD2 на `dim_customer` и `dim_product`** сохраняет историчность (нужно для сопоставления транзакции с
  сегментом клиента или условиями продукта на момент операции, а не текущими), что решает задачу
  регуляторной отчётности без усложнения схемы до снежинки.
