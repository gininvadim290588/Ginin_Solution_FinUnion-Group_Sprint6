# DWH на PostgreSQL vs Data Lakehouse — детальное сравнение для кейса

## Сравнение применительно к FinUnion + RetailBank

| Критерий | DWH на PostgreSQL | Data Lakehouse |
|---|---|---|
| Объём данных | Комфортно для агрегатов и регламентированных витрин; тяжело для полной истории транзакций двух банков | Рассчитан на большие объёмы, дешёвое хранение поверх объектного хранилища |
| Скорость внедрения | Быстро — минимальная новая инфраструктура, знакомый SQL-стек | Дольше — требует настройки Iceberg-каталога, Spark/Trino, партиционирования |
| Регламентированная отчётность | Сильная сторона: строгая схема, ACID, воспроизводимость цифр для регулятора | Возможна через Trino, но исторически такие гарантии требуют больше дисциплины (compaction, snapshot-изоляция) |
| Событийные/сырые данные (клик-стрим, полная история карт) | Не подходит как основное место хранения | Прямое назначение — открытый формат, schema evolution, работа с полуструктурированными данными |
| Риск-модели / ML на исторических данных | Ограниченно, дорого при больших выборках | Хорошо — Spark/Trino поверх тех же Iceberg-таблиц без выгрузки в отдельный слой |
| Стоимость хранения истории | Выше (реляционное хранилище) | Ниже (объектное хранилище + открытый формат) |
| Готовность закрыть проблему "нет Data Lake у RetailBank" | Не решает | Прямо решает |

## Выбранный подход по горизонтам

### Промежуточное состояние (3 месяца) — DWH на PostgreSQL

На 3 месяца выбран **DWH на PostgreSQL** как единственное аналитическое хранилище. Причины:
- Нужен быстрый результат: минимальный работоспособный ландшафт для совместной отчётности по клиентам,
  счетам, продуктам и операциям — именно то, что требует промежуточное состояние кейса.
- Объём данных, необходимый для управленческой отчётности на этом горизонте (агрегаты, а не полная сырая
  история), укладывается в возможности PostgreSQL.
- Внедрение Lakehouse-инфраструктуры (Iceberg-каталог, Spark/Trino, потоковые пайплайны) за 3 месяца
  одновременно с MDM и матчингом клиентов — избыточная нагрузка на проект; лучше сначала стабилизировать
  клиентские данные.
- Простой batch-пайплайн для этого состояния описан в `data-pipelines.md` (пайплайн №2).

### Целевое состояние (12 месяцев) — Data Lakehouse как основное хранилище, DWH сохраняется

К 12 месяцам основным хранилищем для больших исторических и событийных данных становится **Data
Lakehouse на базе Apache Iceberg**, а **DWH сохраняется**, но его роль сужается до регламентированной
отчётности:
- **DWH (PostgreSQL или её целевая эволюция)** — управленческая и регуляторная отчётность: агрегированные,
  историзированные (SCD2) витрины с воспроизводимыми цифрами для регулятора и финансового департамента.
  Здесь важна не гибкость схемы, а стабильность и аудируемость.
- **Data Lakehouse** — полный поток транзакций и событий, история карточных операций до слияния, клиентские
  события каналов, сырьё для риск-моделей и антифрода. Здесь важен объём, гибкость схемы и доступ для
  ML/аналитиков без выгрузки в отдельные системы.

## Роль Apache Iceberg и Trino

- **Apache Iceberg** — формат таблиц поверх объектного хранилища, который даёт Lakehouse то, чего не хватало
  классическому Data Lake: ACID-транзакции, snapshot-изоляцию (важно для сверки сумм и аудита), schema
  evolution (можно добавлять поля без переписывания всей таблицы — критично при постепенной миграции
  RetailBank), партиционирование и compaction для контроля производительности при росте объёма. Iceberg-
  таблицы используются для истории транзакций, карточных операций и событий клиентских каналов.
- **Trino** — распределённый SQL-движок, который выполняет две роли: (1) даёт BI и аналитикам единый SQL-
  доступ к Iceberg-таблицам без необходимости писать Spark-код; (2) выполняет федеративные запросы,
  объединяющие DWH и Lakehouse в одном SQL-запросе, что позволяет BI не выбирать заранее, "где" лежат
  данные, а обращаться к логическому слою поверх обоих хранилищ.

## Что остаётся в DWH, что уходит в Lakehouse

| Данные | Хранилище | Почему |
|---|---|---|
| Регламентированные витрины по Клиенту, Счёту, Продукту, Кредиту (агрегаты) | DWH | Нужна строгая схема, воспроизводимость, соответствие регуляторным формам |
| Полная история транзакций (в т.ч. до слияния, обеих организаций) | Lakehouse | Объём, нужен доступ для риск-моделей и антифрода на детальном уровне |
| История карточных операций FU + RB | Lakehouse | Большой объём, полуструктурированные архивные выгрузки RB |
| Клиентские события каналов (мобильное/веб) | Lakehouse | Высокочастотные, полуструктурированные, не нужны в регламентированной отчётности |
| Регуляторная отчётность (выходной агрегат) | DWH | Формируется из регламентированных витрин DWH, а не напрямую из Lakehouse |
| Данные для ad-hoc аналитики и ML на истории | Lakehouse (через Trino/Spark) | Гибкость схемы, отсутствие необходимости заранее моделировать все возможные запросы |

## Ограничения выбранного подхода

- **Два хранилища вместо одного** увеличивают операционную сложность: нужно поддерживать согласованность
  между агрегатами в DWH и детальными данными в Lakehouse (риск расхождения при сбое ETL-пайплайна
  агрегации).
- **Trino как единая точка доступа** становится критичным компонентом — его недоступность влияет и на BI,
  и на федеративные запросы; требует отдельного SLA и мониторинга.
- **Iceberg требует инженерной дисциплины**: без регулярного compaction и управления партициями
  производительность деградирует при росте объёма данных с двух организаций.
- **Миграция PostgreSQL DWH на целевую платформу** (при росте нагрузки регламентированной отчётности) не
  входит в рамки 12-месячного горизонта этого проекта и потребует отдельной оценки (например, переход на
  MPP-СУБД или колоночное хранилище), если объём регламентированной отчётности вырастет.
- Гибридный подход **дороже**, чем единственное решение (DWH-only или Lakehouse-only), с точки зрения
  количества поддерживаемых компонентов, что обосновано только потому, что закрывает разные, не
  взаимозаменяемые классы задач кейса (регламентированная отчётность vs большие событийные данные).
