# Пайплайны данных

## Основные пайплайны

| Пайплайн | Источник | Приёмник | Тип | Инструменты |
|---|---|---|---|---|
| Клиентские данные (матчинг и золотая запись) | FU CRM, RB CRM | MDM Customer Hub | ETL/ELT (CDC + matching) | Airflow (оркестрация), Debezium (CDC), MDM matching engine, dbt (постобработка) |
| Регламентированная отчётность DWH (промежуточное состояние, 3 мес.) | FU Core, RB Core | DWH на PostgreSQL | Batch ETL, ночной | Airflow, SQL-скрипты / dbt, PostgreSQL `COPY`/FDW |
| Потоковая загрузка транзакций в Lakehouse | FU Core/Cards, RB Core/Cards (через Kafka) | Data Lakehouse (Iceberg) | Streaming / CDC | Debezium, Kafka, Spark Structured Streaming, Apache Iceberg |
| Кредитный портфель для риск-отчётности | FU Loans, RB Loans | DWH | Batch ETL, ежедневный | Airflow, dbt |
| Обращения клиентов в поисковый индекс | Contact Center / Case-система | Поисковый движок | Near real-time ETL | Kafka Connect, индексатор (OpenSearch/Elasticsearch) |
| Агрегация Lakehouse → DWH (сводные витрины) | Data Lakehouse | DWH | Batch ELT | Airflow, Trino (SQL поверх Iceberg), dbt |

Пайплайн для DWH на PostgreSQL (промежуточное состояние, 3 месяца) — простой, поскольку на этом горизонте
не используется Kafka/CDC: данные выгружаются напрямую из FU Core и RB Core по расписанию, преобразуются
в единую схему (звезда, см. `analytical-model.md`) и загружаются в PostgreSQL. Именно этот пайплайн
закрывает требование "минимальный набор витрин для BI" промежуточного состояния кейса.

## Сценарии обработки больших исторических и событийных данных

### Сценарий 1. История карточных операций FU + RB

| Поле | Значение |
|---|---|
| Источник данных | FU Cards (действующая система), RB Cards (архивные выгрузки после слияния, частично CSV/XML) |
| Характер данных | Исторические, большой объём (несколько лет операций двух банков), частично полуструктурированные (архивные выгрузки RB) |
| Целевое хранилище | Data Lakehouse (Iceberg-таблицы) — детальный уровень; агрегаты — в DWH |
| Способ обработки | Разовая batch-миграция истории (ETL: извлечение из архивов RB, приведение к единой схеме, запись в Iceberg) + далее CDC/streaming для новых операций из единой карточной платформы |
| Потребители | BI (карточная аналитика), риск-менеджмент (скоринг на основе истории), антифрод (граф операций), регуляторная отчётность (через агрегацию в DWH) |

Обоснование: до миграции у RetailBank карточная история хранится в RB DWH и точечных выгрузках без единого
формата (проблема, отмеченная в кейсе). Lakehouse с Iceberg позволяет загрузить историю "как есть", а затем
эволюционировать схему по мере приведения к единому стандарту, не блокируя доступ аналитиков и риск-
моделей к уже загруженным данным.

### Сценарий 2. События клиентских каналов (мобильное и веб-приложение)

| Поле | Значение |
|---|---|
| Источник данных | Мобильное приложение и веб-приложение FinUnion и RetailBank (клик-стрим, сессии, действия пользователя) |
| Характер данных | Событийные, высокочастотные, полуструктурированные (JSON) |
| Целевое хранилище | Data Lakehouse (Iceberg), Kafka как промежуточный буфер |
| Способ обработки | Streaming: события публикуются в Kafka в момент действия пользователя, Spark Structured Streaming пишет их в Iceberg-таблицы с партиционированием по дате |
| Потребители | BI/маркетинг (поведенческая аналитика, конверсии по каналам), риск-менеджмент/антифрод (аномальное поведение в сессии как сигнал мошенничества), продуктовые команды (UX-аналитика) |

Обоснование: такие данные не нужны в регламентированной отчётности (не идут в DWH напрямую), но обладают
высокой ценностью для антифрода и продуктовой аналитики — типичный случай, где Lakehouse избавляет от
необходимости заранее проектировать жёсткую реляционную схему для данных, чья структура может меняться
(новые типы событий добавляются мобильным/веб-приложением без согласования с DWH-командой).
