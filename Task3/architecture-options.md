# Сравнение архитектурных вариантов

## 1. DWH на PostgreSQL

**Плюсы**
- Быстрый старт: знакомая технология для команды ИТ (SQL Server / реляционный опыт уже есть у Vadim-подобных
  специалистов в компании), низкий порог входа.
- Строгая схема и ACID-транзакции — удобно для регламентированной отчётности, где нужна воспроизводимость
  цифр.
- Зрелая экосистема BI-инструментов, простое администрирование, встроенные средства резервного копирования.
- Низкая стоимость для умеренных объёмов данных.

**Минусы**
- Плохо масштабируется горизонтально для больших объёмов исторических/событийных данных (годы транзакций
  двух банков).
- Нет нативной поддержки полуструктурированных и потоковых данных в промышленных объёмах.
- Жёсткая схема усложняет добавление новых источников (например, клик-стрим каналов) без миграций.
- Дорого держать "холодную" историю в реляционной БД (стоимость хранения выше, чем в объектном хранилище).

**Когда подходит.** Когда объём данных умеренный, требования — прежде всего регламентированная отчётность
с фиксированной схемой, а событийная/сырая аналитика не является приоритетом.

**Применимость к кейсу.** Хорошо подходит как **временное** решение на 3 месяца (промежуточное состояние):
нужно быстро получить единую отчётность по клиентам/счетам/продуктам/операциям без длительного внедрения
Lakehouse. Не подходит как единственное целевое хранилище на 12 месяцев — не выдержит объём истории двух
банков и требований риск-моделирования на сырых событийных данных.

## 2. Data Lakehouse

**Плюсы**
- Единая платформа для сырых, исторических и событийных данных с открытым форматом таблиц (Iceberg) —
  избавляет от дублирования "Lake + Warehouse".
- Горизонтальное масштабирование, дешёвое хранение поверх объектного хранилища.
- Поддержка ACID-транзакций и schema evolution поверх Iceberg — снимает главный исторический недостаток
  Data Lake ("data swamp").
- Один и тот же слой данных обслуживает и BI (через Trino), и риск-модели/ML (через Spark).

**Минусы**
- Более сложная эксплуатация и оркестрация, чем классический DWH.
- Требует зрелой инженерной культуры (управление партиционированием, compaction, каталогом таблиц).
- Регламентированная отчётность с жёсткими SLA и построчной аудируемостью реализуется сложнее, чем в
  классическом DWH с устоявшейся звёздной схемой.

**Когда подходит.** Когда объём и разнообразие данных велики (структурированные + событийные +
полуструктурированные), а потребители — не только BI, но и риск-модели, антифрод, ML.

**Применимость к кейсу.** Прямо закрывает две проблемы кейса: "Data Lake есть только частично" у FinUnion и
полностью отсутствует у RetailBank. Хорошо подходит для истории карточных операций, клиентских событий
каналов и в целом для целевого (12 мес.) хранения больших объёмов.

## 3. Data Mesh

**Плюсы**
- Устраняет узкое место центральной команды данных — домены (Party, Account & Lending, Payments, Card,
  Servicing) сами владеют своими data-продуктами и отвечают за их качество.
- Хорошо ложится на организационную структуру банка после слияния: у FinUnion и RetailBank уже разные
  бизнес-направления с разной экспертизой в своих данных.
- Ускоряет разработку новых аналитических кейсов, так как не всё идёт через единый DWH-конвейер.

**Минусы**
- Требует зрелой платформенной инфраструктуры (self-service, стандарты интероперабельности) — банк, только
  что переживший слияние с разрозненными данными, ещё не готов к полностью децентрализованной модели.
- Риск повторения проблемы кейса "на новом уровне": без сильного governance домены могут снова разойтись
  в форматах и терминологии — та же проблема, что привела к текущей рассинхронизации FU/RB.
- Сложнее обеспечить единую регуляторную отчётность, если каждый домен ведёт данные по-своему.

**Когда подходит.** В организациях с высокой зрелостью данных, множеством независимых доменных команд и
устоявшимися платформенными стандартами.

**Применимость к кейсу.** Полноценный Data Mesh **преждевременен** для FinUnion + RetailBank на горизонте
12 месяцев — сначала нужна консолидация (MDM, единый DWH/Lakehouse), иначе домены унаследуют текущий
разнобой. Но **элементы** Data Mesh (доменные data-продукты поверх общей платформы) применимы уже сейчас —
это раскрыто в `data-products.md`.

## Итоговый выбор: гибридная архитектура

**Выбран гибридный подход: DWH (на первом этапе — PostgreSQL) + Data Lakehouse, с элементами Data Mesh
поверх общей платформы.**

Обоснование:
- **3 месяца** — DWH на PostgreSQL закрывает срочную потребность в единой регламентированной отчётности
  без длительного внедрения Lakehouse-инфраструктуры (см. `dwh-lakehouse.md` для деталей).
- **12 месяцев** — Data Lakehouse (Iceberg + Trino) становится основным хранилищем для больших исторических
  и событийных данных, DWH сохраняется для регламентированной отчётности с жёсткими SLA и аудируемостью
  (может быть реализован поверх той же платформы через Trino-представления или мигрировать на MPP-решение
  при росте нагрузки — вне рамок данного задания).
- **Data Mesh как организационная надстройка**, а не как замена технологической платформе: доменные команды
  (Party, Account & Lending, Payments, Card, Servicing) владеют своими data-продуктами, публикуемыми поверх
  единого DWH/Lakehouse и каталогизируемыми в DataHub — то есть используется governance-модель Data Mesh
  без полной децентрализации инфраструктуры, что снижает риск повторного расхождения данных после слияния.

Чистый DWH на PostgreSQL как единственное целевое решение отклонён из-за ограниченной масштабируемости для
истории двух банков. Чистый Data Mesh отклонён как преждевременный для организации, ещё не завершившей
базовую консолидацию данных.
