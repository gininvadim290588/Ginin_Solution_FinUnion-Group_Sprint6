# Task 3. Целевая архитектура данных и аналитическая платформа — FinUnion + RetailBank

## Цель

Спроектировать целевую (12 месяцев) архитектуру данных объединённого банка: операционные хранилища,
аналитическую платформу, пайплайны данных, каталог данных и модель управления, сравнить архитектурные
подходы и обосновать выбор, спроектировать аналитическую модель и доменные data-продукты.

## Краткое резюме решений

- **Целевая архитектура** объединяет все девять требуемых компонентов: консолидированные Operational
  Systems, MDM (Customer Hub + Reference Data), Integration Layer (sync API/ESB + CDC), Kafka как
  событийная шина, DWH для регламентированной отчётности, Data Lakehouse (Iceberg) для больших данных, BI
  поверх обоих хранилищ через Trino, Airflow для batch-оркестрации, DataHub как единый каталог и источник
  lineage.
- **Архитектурный выбор — гибрид.** DWH на PostgreSQL закрывает промежуточное состояние (3 месяца) как
  быстрый, знакомый инструмент для регламентированной отчётности. Data Lakehouse становится основным
  хранилищем для больших исторических и событийных данных к 12 месяцам. Полноценный Data Mesh признан
  преждевременным для организации, ещё не завершившей консолидацию данных, но его элементы (доменные
  data-продукты с чёткими владельцами) используются поверх общей платформы.
- **Iceberg и Trino.** Iceberg даёт Lakehouse ACID-транзакции, snapshot-изоляцию и schema evolution —
  решает проблему "data swamp" и позволяет постепенно мигрировать историю RetailBank. Trino — единая точка
  SQL-доступа для BI и федеративных запросов между DWH и Lakehouse.
- **Пайплайны.** Описано 6 пайплайнов, включая простой batch-пайплайн для DWH на PostgreSQL промежуточного
  состояния (3 месяца), и 2 сценария больших данных: история карточных операций (batch-миграция + CDC) и
  события клиентских каналов (streaming через Kafka в Iceberg).
- **Аналитическая модель.** Звёздная схема для области "Транзакции" — `fact_transactions` и 8 измерений
  (customer, account, card, product, branch, channel, counterparty, date); звезда выбрана вместо снежинки
  ради простоты BI-запросов и совместимости с self-service инструментами.
- **Data-продукты.** 5 доменных data-продуктов (Customer 360, Account & Lending 360, Payments &
  Transactions Stream, Card Portfolio, Customer Servicing & Cases), каждый привязан к BIAN-домену из
  Task 1 и владельцу из матрицы Task 2, публикуется поверх общей платформы, а не отдельной инфраструктуры.

## Как читать документы

Рекомендуемый порядок: `target-data-architecture.md` (+ диаграмма) → `architecture-options.md` →
`dwh-lakehouse.md` → `data-pipelines.md` → `analytical-model.md` (+ диаграмма) → `data-products.md`.
Сначала задаётся целостная картина компонентов, затем обосновывается выбор технологического подхода,
детализируется хранение больших данных, показывается, как данные физически перемещаются (пайплайны), как
они моделируются для аналитики (звезда) и, наконец, как домены банка могут владеть своими данными поверх
этой платформы (data-продукты).
