# Референсная модель BIAN

BIAN (Banking Industry Architecture Network) используется здесь не как формальность, а как инструмент трёх
конкретных задач слияния:

1. **Унификация терминологии.** FU и RB называют одни и те же вещи по-разному (например, "договор" vs
   "контракт", разные статусные модели карт). Service Domain из BIAN даёт нейтральный, отраслевой словарь,
   на который можно смэппить оба варианта, не выбирая "чей термин главнее".
2. **Границы владения данными.** Каждый Service Domain в BIAN предполагает владельца процесса и данных —
   это готовый каркас для Data Office, чтобы назначить ответственных за домены данных после слияния, а не
   изобретать модель владения с нуля.
3. **Поиск пересечений между системами FU и RB.** Если FU Loans и RB Loans оба маппятся на один и тот же
   Service Domain (Consumer Loan), это прямое доказательство того, что системы дублируют друг друга и один
   из компонентов может стать целевой мастер-системой, а второй — кандидатом на вывод из эксплуатации.

## Сопоставление сущностей с областями BIAN

| Сущность | Область BIAN (Service Domain) | Зачем это нужно |
|---|---|---|
| Клиент | Party Data Management / Party Reference Data Directory | Единый подход к клиентским данным независимо от того, физлицо это или юрлицо; основа для MDM-модели golden record |
| Счёт | Current Account (в составе Product Family "Deposits & Accounts") | Унификация модели счёта между FU Core и RB Core, единая структура статусов и типов |
| Карта | Card Management / Consumer Payback and Reward | Единая модель карточных продуктов и статусов вместо двух разных наборов в FU Cards и RB Cards |
| Кредит | Consumer Loan / Corporate Lending | Приведение правил кредитных продуктов и определения просрочки/дефолта к единой модели для риск-менеджмента |
| Договор | Party Agreement / Product & Service Agreement | Единая модель юридической фиксации отношений клиент–банк, независимо от продукта |
| Транзакция | Current Account (Servicing) / Payment Execution | Единая модель операционных событий для построения консолидированного DWH и антифрод-аналитики |
| Платёж | Payment Execution / Payment Order | Отраслевой стандарт статусной модели платежа, важный для AML-контроля после объединения платёжных потоков |
| Продукт | Product Directory / Product Deployment | Единый продуктовый каталог — прямая основа для того, чтобы клиенты RetailBank получили доступ к продуктам FinUnion |
| Обращение клиента | Customer Case Management | Единая модель обработки обращений вне зависимости от того, в какой CRM клиент был исторически заведён |
| Отделение | Branch Sales & Service Management | Единый справочник точек обслуживания и их зоны ответственности для региональной отчётности |
| Тариф | Product Pricing / Product Deployment | Приведение тарифных сеток FU и RB к единой модели ценообразования продукта |
| Контрагент | Party Reference Data Directory | Единая модель третьих сторон, общая с моделью клиента, но с признаком "внешний" — основа для антифрод-графа |

## Как это ведёт к целевым доменам данных

Группировка сущностей по BIAN-областям выше уже подсказывает границы будущих доменов данных / data
products для целевой архитектуры:

- **Party domain** — Клиент, Контрагент, Клиентский сегмент (единый MDM-домен, один владелец — Data Office
  совместно с CRM-командами FU и RB).
- **Product & Pricing domain** — Продукт, Тариф (владелец — продуктовые команды розницы и МСБ).
- **Account & Lending domain** — Счёт, Кредит, Договор (владелец — Core Banking / Риск-менеджмент).
- **Payments domain** — Транзакция, Платёж (владелец — операционный блок и комплаенс/AML).
- **Card domain** — Карта (владелец — карточный процессинг).
- **Servicing domain** — Обращение клиента, Отделение (владелец — контактный центр и сеть отделений).

Эта группировка используется дальше в промежуточном (3 месяца) и целевом (12 месяцев) состояниях как основа
для матрицы мастер-систем и назначения владельцев данных.
