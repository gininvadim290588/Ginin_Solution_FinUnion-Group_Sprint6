# Ключевые бизнес-сущности

## 1. Клиент / Party

### Описание

Физическое лицо, индивидуальный предприниматель или юридическое лицо, являющееся клиентом банка либо связанным с банковскими отношениями субъектом.

Для целевой архитектуры рекомендуется использовать более общий термин **Party**, позволяющий моделировать физических лиц и организации единообразно.

### Основные атрибуты

- `party_id` — единый идентификатор;
- `party_type` — физическое лицо / юридическое лицо / ИП;
- ФИО / наименование;
- дата рождения / дата регистрации;
- ИНН;
- СНИЛС — при наличии и необходимости;
- паспортные данные;
- контактные данные;
- адреса;
- статус клиента;
- дата создания;
- дата изменения.

### Связи

- Клиент → Профиль;
- Клиент → Счёт;
- Клиент → Договор;
- Клиент → Карта;
- Клиент → Кредит;
- Клиент → Обращение;
- Клиент → Документ;
- Клиент → Сегмент;
- Клиент → Контрагент;
- Клиент → Relationship.

### Источники

- FU CRM;
- RB CRM;
- FU Core;
- RB Core.

### Критерий включения

Ключевая master-data сущность, вокруг которой формируется единый клиентский профиль.

### Проблемы качества

- дубли клиентов;
- разные идентификаторы;
- разные форматы ФИО;
- различия в форматах адресов;
- пропуски атрибутов;
- устаревшие контактные данные;
- различия в правилах идентификации;
- отсутствие единого master ID.

### Целевое решение

**MDM Party / Customer Master** как golden record.

## 2. Клиентский профиль

### Описание

Совокупность актуальных характеристик клиента, используемых для обслуживания, сегментации, продаж, риск-анализа и формирования единого клиентского представления.

### Основные атрибуты

- `profile_id`;
- `party_id`;
- контактные данные;
- адреса;
- предпочтительные каналы;
- статус обслуживания;
- сегмент;
- признаки согласий;
- KYC-статус;
- дата актуализации.

### Связи

- Клиент;
- Клиентский сегмент;
- Обращение;
- Продукт.

### Источники

- FU CRM;
- RB CRM;
- MDM.

### Критерий включения

Необходима для построения единого Customer 360.

### Проблемы качества

- различающиеся профили одного клиента;
- устаревшие данные;
- разные правила заполнения;
- отсутствие единого источника истины.

### Целевое решение

MDM + Customer Profile.

- тип счёта;
- валюта;
- статус;
- дата открытия;
- дата закрытия;
- остаток;
- `product_id`;
- филиал.

### Связи

- Клиент;
- Договор;
- Продукт;
- Транзакция;
- Платёж;
- Карта.

### Источники

- FU Core;
- RB Core.

### Проблемы качества

- различные модели счетов;
- различные статусы;

- условия договора.

- Продукт;
- Тариф;
- Счёт;
- Кредит;
- Документ.

### Источники

- RB Core;

## 9. Транзакция

### Описание

Фактически проведённая финансовая операция.

Важно различать:

- **Payment** — распоряжение/платёжный процесс;
- **Transaction** — факт финансового движения.

### Основные атрибуты

- `transaction_id`;
- `payment_id`;
- `account_id`;
- дата и время;
- сумма;
- валюта;
- тип операции;
- дебет/кредит;
- статус;
- источник;
- корреспондент;
- идентификатор внешней системы.

### Связи

- Счёт;
- Платёж;
- Карта;
- Клиент;
- Контрагент.

### Источники

- FU Core;
- RB Core;
- FU Cards;
- RB Cards.

### Проблемы качества

- разные идентификаторы;
- различия в кодах операций;
- различные форматы дат;
- различия в справочниках;
- риск дублей при миграции.

### Целевое решение

Операционный источник + историческое хранение в DWH/Lakehouse.

## 17. Клиентская связь / Relationship

### Описание

Связь между клиентами и/или организациями:

- физическое лицо → владелец компании;
- сотрудник → организация;
- компания → дочерняя компания;
- клиент → представитель;
- клиент → поручитель.

### Значение

Особенно важна для:

- AML;
- KYC;
- риск-анализа;
- антифрода;
- корпоративного бизнеса.

При росте требований к анализу связей может использоваться графовая БД.
