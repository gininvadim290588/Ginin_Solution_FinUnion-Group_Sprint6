# Стратегия хранения данных

Для каждого типа хранилища указаны сущности/данные, которые в него попадают, и обоснование выбора.

## OLTP БД — операционные данные

**Данные:** Счёт, Карта, Кредит, Договор, Транзакция (оперативный слой), Платёж (в момент исполнения).

**Обоснование.** Это данные с высокой частотой изменений, требующие строгой транзакционности (ACID) и
низкой задержки — счета и платежи не могут временно "разойтись" с реальным состоянием. Остаются в
существующих FU Core / RB Core (и их преемниках) как системы записи (systems of record); аналитика не
должна создавать на них нагрузку — отсюда обязательное разделение OLTP/OLAP, прямо указанное в целях
проекта.

## MDM — золотые записи клиентов и справочников

**Данные:** Клиент (золотая запись после матчинга FU/RB), Продукт, Тариф, Отделение, Контрагент (частично —
для контрагентов, которые сами являются клиентами или часто повторяются).

**Обоснование.** Это ровно те сущности, для которых кейс явно фиксирует проблему рассинхронизации
("справочники продуктов, тарифов, отделений и клиентских сегментов не синхронизированы", дубли клиентов с
разными идентификаторами). MDM даёт единый client_id и единый продуктовый каталог — прямая бизнес-цель
("единый профиль клиента", "определить мастер-системы"). MDM для клиентов дополнительно хранит правила
сопоставления (matching rules) между FU CRM и RB CRM.

## DWH — регламентированная отчётность и BI

**Данные:** агрегированные и историзированные срезы Счёта, Кредита, Транзакции, Платежа, Клиента (SCD2) для
управленческой и регуляторной отчётности.

**Обоснование.** Регулятору и финансовому департаменту нужны стабильные, воспроизводимые, аудируемые
цифры — DWH с чётко определённой моделью (звезда/снежинка) и историзацией лучше подходит для этого, чем
Data Lakehouse, где схема более гибкая. DWH также остаётся источником для FU BI / RB BI на переходный
период, пока витрины не объединены.

## Data Lakehouse — большие исторические и событийные данные

**Данные:** полный поток Транзакций и событий (в том числе не вошедших в регламентированную отчётность),
исторические выгрузки RB DWH и FU Data Lake, лог обращений клиентов, сырые данные для риск-моделей и
скоринга.

**Обоснование.** Риск-менеджменту и аналитикам нужен доступ к сырым, гранулярным, долгоживущим данным для
построения моделей (скоринг, антифрод), что избыточно и дорого держать в DWH. Lakehouse также решает
проблему кейса "Data Lake есть только частично, у RetailBank его нет вообще" — это целевая платформа для
обеих организаций.

## Объектное хранилище — документы и архивы

**Данные:** сканы Договоров, приложенные документы по Обращениям клиентов, архивные batch-выгрузки, файлы
подтверждающих документов по Кредитам (обеспечение).

**Обоснование.** Неструктурированные и полуструктурированные файлы не должны храниться в реляционных
системах; объектное хранилище с версионированием и retention-политиками закрывает требование
"персональные и финансовые данные должны быть защищены" за счёт шифрования на уровне бакетов и контроля
доступа.

## Графовая БД — связи клиентов и контрагентов

**Данные:** Клиент ↔ Контрагент ↔ Транзакция/Платёж/Кредит (поручительство).

**Обоснование.** Обосновано напрямую сущностью **Контрагент**: связи "клиент — контрагент — другой клиент"
образуют граф, который нужен для антифрод-анализа (выявление цепочек подставных операций) и для риск-
менеджмента (связанные заёмщики/поручители). Реляционная модель плохо масштабируется на многошаговые
графовые запросы ("найти все транзакции клиента с контрагентами, связанными с другим проблемным клиентом
через 2 шага") — граф решает это нативно.

## Поисковый движок — обращения и клиентские данные

**Данные:** Обращение клиента (свободный текст), частично — история взаимодействий с клиентом из CRM.

**Обоснование.** Обосновано контактным центром: свободнотекстовые обращения плохо ищутся и группируются в
реляционной БД. Полнотекстовый поисковый движок (с индексами по теме, статусу, продукту) ускоряет работу
операторов контакт-центра и позволяет строить аналитику по частотным темам обращений — что напрямую влияет
на качество обслуживания при интеграции продуктовых линеек.

## Сводная таблица

| Тип хранилища | Основные сущности | Ключевая причина |
|---|---|---|
| OLTP БД | Счёт, Карта, Кредит, Договор, Транзакция, Платёж | Транзакционность, низкая задержка, системы записи |
| MDM | Клиент, Продукт, Тариф, Отделение | Единый идентификатор и устранение дублей/рассинхронизации |
| DWH | Историзированные срезы для отчётности | Регуляторная и управленческая отчётность, аудируемость |
| Data Lakehouse | Полный поток событий, история, сырые данные для риска | Объём, гибкость схемы, риск-модели |
| Объектное хранилище | Документы, сканы, архивы | Неструктурированные данные, retention |
| Графовая БД | Контрагент, связи Клиент↔Контрагент | Многошаговые связи для антифрода |
| Поисковый движок | Обращение клиента | Полнотекстовый поиск и аналитика по темам |
